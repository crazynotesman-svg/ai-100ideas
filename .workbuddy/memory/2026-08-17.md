# 2026-08-17 — 削减 DeepSeek token 成本（sync pipeline 降频 + 缓存修复）

## 起因
队长反馈"worker 执行频率高、消耗 token 多"。澄清：Cloudflare Worker 本身不烧 token
（按请求计费、无 Cron Trigger，已 grep 确认 `wrangler.toml` 无 `crons`）。真正的开销在
`daily-sync.yml` → DeepSeek 富化。

## 根因（比降频更严重）
`scripts/.cache/` 在 `.gitignore` 里，且 `git ls-files` 确认未被跟踪。GitHub Actions
每次 `actions/checkout` 都是全新工作区 → `seen.json` 永远不存在 → `needsProcessing()`
对全部 ~354 个仓库返回 true → **每天把整个目录重新喂给 DeepSeek**。
按 ~3.5k input tokens/repo 估算 ≈ 124 万 tokens/天。降频只能线性改善，缓存才是数量级。

## 改动
1. `.github/workflows/daily-sync.yml`
   - cron `0 2 * * *` → `0 2 * * 1,4`（周一+周四 02:00 UTC）
   - **加 `actions/cache@v4`** 持久化 `scripts/.cache`，key=`sync-dedup-${{ github.run_id }}`
     + `restore-keys: sync-dedup-`（滚动 key 模式：每次写新条目、按前缀取最近一次）
   - 加 `MAX_REPOS`（默认 60）与 `FORCE_REENRICH` 环境变量
   - `workflow_dispatch` 加 `max_repos` / `force_reenrich` 输入
   - 显示名改为 `Content Sync (GitHub → DeepSeek → D1)`（**文件名保留** `daily-sync.yml`
     以保住 Actions 历史，且 DEPLOY.md 多处引用）
2. `scripts/run-pipeline.ts`
   - `STAR_CHANGE_THRESHOLD = 50` → `max(STAR_CHANGE_ABS=200, 缓存star × 15%)`
   - 加 `MIN_REFRESH_DAYS = 30` 冷却期
   - `MAX_REPOS` 环境变量作为 `--max-repos` 默认值（CLI 优先），加 `--force`
   - 缓存为空时打印显式告警；结尾打印 `est. DeepSeek input tokens: ~N`
3. `scripts/enrich.ts`：README 送入 `10_000` → `README_PROMPT_CHARS`（默认 6000，
   可用 `ENRICH_README_CHARS` 覆盖）
4. `DEPLOY.md` §5 重写为成本模型表 + 两条排障行

## 为什么不是每周一次（重要坑）
GitHub 的 Actions cache **7 天不被访问就淘汰**。正好每周的 cron 卡在淘汰边界上，
会反复丢失去重状态——丢缓存的代价远大于多跑一次。所以选每周两次（间隔 3-4 天）保温。

## 验证（离线 fixture，未消耗 API）
`astro check` 0 错误 + 5 个场景全通过：
- 空缓存 → 3/3 全新（并打印 EMPTY 告警）
- 缓存 2 天前 → 0 to enrich（冷却期拦住）
- 缓存 40 天前但 dify +2000 star（阈值 11400）→ 仍跳过 ← **旧逻辑会全部重跑**
- `MAX_REPOS=2` → 限 2 个，剩 1 个滚到下轮
- `FORCE_REENRICH=true` → 绕过缓存全跑
测试辅助脚本写在 `scripts/.cache/mkcache.ts`（gitignored），跑完已删。
注意：Windows 下 `/tmp` 映射到 `D:\tmp`，tsx 导入会 ERR_MODULE_NOT_FOUND，临时脚本要放工作区内。

## 预期效果
稳态每轮只富化真正的新仓库（通常 <20 个），约 4 万 tokens/轮 × 每周 2 轮
≈ 从 3700 万/月 降到 ~30 万/月（约 99%）。最坏情况（缓存丢失）由 MAX_REPOS=60 兜底。
